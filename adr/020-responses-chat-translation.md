# ADR 020: Translating between the Responses API and chat providers

Status: Accepted

ADR issue: pridkett/simple-llm-proxy#167
Implementation issues: pridkett/simple-llm-proxy#168, pridkett/simple-llm-proxy#169

Builds on [ADR 010](010-openai-responses-api.md) (Responses passthrough) and
[ADR 014](014-anthropic-messages-api.md) (Messages for any chat provider).

## Context

The proxy speaks three client dialects: OpenAI Chat Completions, Anthropic
Messages, and OpenAI Responses. Two of them already cross providers:

| Client dialect | Upstream | Today |
|---|---|---|
| Chat Completions | any chat provider, including Anthropic | works |
| Messages | any chat provider, including OpenAI | works (ADR 014) |
| Responses | OpenAI, MiniMax | passthrough (ADR 010) |
| Responses | Anthropic, Gemini, Ollama, vLLM, OpenRouter | 400 `model does not support the Responses API` |
| Chat Completions or Messages | a model served only over Responses | unreachable; the proxy always calls `/chat/completions` |

Both gaps matter in practice. Responses-only clients (the Codex CLI, the OpenAI
Agents SDK defaults) cannot use a Claude or local model through the proxy, and
chat or Messages clients (Claude Code, most libraries) cannot use the OpenAI
models that are published only on the Responses API.

## Decision

Chat Completions stays the hub. Every dialect already converts to and from
`model.ChatCompletionRequest`; Responses gets the same two converters, in a new
provider-neutral package `internal/responsesbridge`. No dialect pair gets its
own converter: Messages to a Responses-only model is Messages → chat →
Responses.

### 1. Responses clients on chat-only providers (#168)

`responsesbridge.FromChat(p)` wraps any `provider.Provider` as a
`provider.ResponsesProvider`. The `/v1/responses` handler uses the wrapper only
when the routed deployment does not implement the interface itself, so OpenAI
and MiniMax keep their lossless passthrough. Routing, accounting, logging and
failover are untouched because the wrapper sits below them.

Request mapping:

- `instructions` becomes a leading system message. A string `input` becomes one
  user message.
- Input items: `message` items map by role (`developer` becomes `system`) with
  `input_text`, `output_text`, `refusal` and `input_image` parts;
  `function_call` items become assistant `tool_calls` (adjacent calls share one
  assistant message); `function_call_output` becomes a `tool` message.
- `reasoning` items are dropped. They are opaque to every other provider and
  cannot be replayed.
- `max_output_tokens`, `temperature`, `top_p`, `parallel_tool_calls` and `user`
  carry over. `text.format` becomes `response_format`. `reasoning.effort`
  becomes `reasoning_effort`, which OpenAI-compatible upstreams understand and
  the native adapters ignore.
- Function tools and `tool_choice` are re-nested into the chat shape.

Rejected with HTTP 400, because silently ignoring them would change what the
caller gets:

- `background: true`, `previous_response_id` and `conversation`. The proxy
  keeps no conversation state and a chat provider has no job to poll.
- Built-in tools (`web_search`, `file_search`, `code_interpreter`,
  `image_generation`, `computer_use`, `mcp`, custom tools) and
  `item_reference` or other unknown input items.
- File inputs (`input_file`) and audio.

Rejections carry status 400 so the router treats them as invalid input and does
not cool down a healthy deployment (`provider.IsInvalidRequest`).

Response mapping: one `message` item with an `output_text` part when there is
text, then one `function_call` item per tool call. `finish_reason: length`
becomes `status: incomplete` with `incomplete_details.reason:
max_output_tokens`; `content_filter` likewise. Usage is reported as
`input_tokens`/`output_tokens`. Ids are generated by the proxy (`resp_…`,
`msg_…`, `fc_…`) and are not retrievable; `store` is ignored and
`GET /v1/responses/{id}` returns 404 for them, as it does for any response
that was not a background job.

Streaming emits the documented event sequence incrementally from chat chunks:
`response.created`, `response.in_progress`, then per item
`response.output_item.added`, `response.content_part.added`,
`response.output_text.delta`…, the matching `.done` events, and
`response.function_call_arguments.delta`/`.done` for tools, ending in
`response.completed` or `response.incomplete` carrying the full response and
usage. The upstream chat stream is always asked for usage.

### 2. Chat and Messages clients on Responses-only models (#169)

A deployment opts in with the LiteLLM model-string convention:

```yaml
- model_name: gpt-5-pro
  litellm_params:
    model: openai/responses/gpt-5-pro
    api_key: os.environ/OPENAI_API_KEY
```

The router strips the `responses/` segment and wraps the provider with
`responsesbridge.ToChat(p)`, whose `ChatCompletion` and `ChatCompletionStream`
call the provider's own `CreateResponse`/`CreateResponseStream`. The provider
must implement `provider.ResponsesProvider`; otherwise the config fails to
load. The wrapper still exposes the native Responses methods, so `/v1/responses`
on that alias remains a passthrough. Opt-in is explicit rather than inferred
from the model name, in line with ADR 016's rule that capability never comes
from guessing.

Request mapping is the inverse of section 1: messages become input items in
order (system messages stay in place as `system` items rather than being
hoisted into `instructions`), tools and `tool_choice` are flattened,
`max_completion_tokens`/`max_tokens` become `max_output_tokens`,
`response_format` becomes `text.format`, and `reasoning_effort` becomes
`reasoning.effort`. The request is sent with `store: false`; the proxy never
reads the stored copy, so asking the upstream to keep one would only widen data
retention.

Rejected with HTTP 400: `n` greater than 1 and `stop`, neither of which the
Responses API can express. Legacy `functions`/`function_call` are also rejected.

Response mapping: text from `message` items is concatenated into the assistant
content, `function_call` items become `tool_calls`, reasoning and built-in tool
items are dropped. `finish_reason` is `tool_calls` when calls are present,
`length` or `content_filter` for an `incomplete` response, otherwise `stop`. A
`failed` response is an upstream error. Streaming maps text and argument deltas
to chat chunks and ends with a finish chunk and a usage chunk.

## Alternatives

- **A converter per dialect pair** (Responses ⇄ Messages directly) would keep
  reasoning blocks and server tools that chat cannot represent, but needs a
  converter for every pair and every new dialect. The hub loses those features
  for translated routes only; native routes are unaffected.
- **Translating in the handler**, as `/v1/messages` does, would duplicate the
  Responses handler's background and accounting paths. Wrapping the provider
  keeps the handler change to one branch.
- **Emulating `previous_response_id`** by storing transcripts would make the
  proxy a conversation store with retention and access-control obligations.
  Out of scope; clients must send full history, which Responses allows.
- **Auto-detecting Responses-only models** by name would break silently when
  OpenAI's catalogue changes.

## Consequences

- Any client dialect can reach any generation deployment, with the losses
  listed above on translated routes.
- Translated Responses are stateless: no background jobs, no retrieval, no
  server-side conversation chaining.
- Cost accounting on translated routes uses token usage and the cost map as
  chat does; upstream-reported cost is used where the underlying call supplies
  it.
- The `responses/` model prefix is reserved for providers that implement the
  Responses API.
